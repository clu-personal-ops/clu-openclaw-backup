# Hourly Sol usage monitor with Claude fallback context

The existing hourly check now reads Claude subscription quota directly from `https://api.anthropic.com/api/oauth/usage`, using the installed native Claude Code credential accessor. Credentials stay in memory and existing storage; the monitor never prints, copies, refreshes or replaces them. The GET uses a 12-second timeout and no inference. Strict finite 0–100 percentages are required for both five-hour and weekly windows; applicable Sonnet windows/model limits also gate headroom. Missing/malformed/error data is unknown, never availability. Extra paid usage is not enabled by this monitor.

Existing Sol notices include fresh Claude headroom or cooldown plus remaining percentages and exhausted-window recovery when provided. Claude cooldown/reset changes, recovery and retrieval-failure/recovery generate independent deduplicated notices on the same hourly check; quiet healthy checks remain silent. Claude recovery is checked hourly, not via a new Claude-specific expiration job. Sol expiration reminders remain unchanged. The monitor does not switch models or resume sessions. Native credential accessor discovery is installation-version dependent; after an OpenClaw update, a missing/changed accessor safely produces unknown and requires revalidation. Expired tokens require the existing Claude login lifecycle; this monitor does not refresh them.

Validation: authenticated API GET returned HTTP 200, five-hour and weekly utilization both 0%; integrated adapter independently read 100% remaining for each. Existing 27 scenarios and separate `node scripts/claude-usage.test.mjs` cover strict schema, Sonnet limits, independent Claude transitions, preserved last-known state on retrieval error and quiet duplicate checks. No notifications or inference calls used for validation. Backups before the extension: `backups/usage-monitor-claude-20261112`; restore those script/test/docs and remove `scripts/claude-usage.mjs` / `scripts/claude-usage.test.mjs` to undo the extension while retaining the fail-closed Sol repair.

The existing automation `0691547a-cc3e-4b7a-a928-f37ea96800f9` runs `usage-monitor.mjs` directly as a native **command** payload every 3,600,000 ms. Its original cadence anchor is preserved. It does not call a model, inspect failed sessions, or resume tasks. Native scheduler delivery sends real transition text to the existing Telegram/default conversation; `NO_REPLY` suppresses normal availability messages.

The read-only `usage.status` RPC uses the existing authenticated provider integration. The monitor requires a fresh timestamp (at most 90 seconds old), no provider error, and numeric short-term plus weekly windows. Stale-while-revalidate responses are retried for up to 70 seconds rather than treated as current. At expiration the snapshot must also be timestamped at/after that expiration. The weekly remainder is `100 - usedPercent`, not token arithmetic or a guess. It is provider-reported percentage precision.

A cooldown is any reported usage window at 100%. Recovery time is the latest future provider reset of all exhausted windows. If an exhausted window lacks a future reset, time is unknown. A window under 100% after a previously confirmed cooldown is a restoration, including early/manual reset. These are usage observations, not inference success probes or guarantees about provider/network/auth health.

State is atomically saved in `state/usage-monitor.json`. Only entry/exit, changed recovery time, retrieval failure/recovery and the one expiration check produce output. Weekly consumption changes alone do not repeat a cooldown notice. Retrieval errors preserve the last confirmed state and pending reminders, but now fail the native command (nonzero exit) on every unavailable observation instead of being recorded as a successful quiet check. The existing failure-alert route and cooldown own error delivery; a successful later retrieval reports recovery. Normal hourly scheduling remains unchanged.

While cooling down with a known future reset, exactly one pending native one-shot is reconciled under declaration prefix `openai-usage-expiration:<hourly job id>:`. It calls the same script at the expected reset with `--expiration <milliseconds>`, verifies actual usage rather than claiming recovery from elapsed time, and auto-deletes on successful timer-fired completion. A new reset replaces the pending reminder; early restoration cancels it. A queued stale reminder checks saved state and returns silently. The active expiration job is not removed from within itself, preserving native completion delivery. Different reset timestamps use different idempotency keys so an executing old one-shot cannot replace a newer reminder.

Limits: early/manual resets are detected at the next hourly check (or pending expiration), not continuously. A provider-reported reset is expected time, not a promise; exhausted usage after expiration is reported honestly. The Gateway, network, native command execution and Telegram must be functioning. Local transition state is committed before native delivery, so a delivery failure is surfaced by the native failure alert but cannot provide transactional exactly-once messaging across crashes/network ambiguity. No Gateway restart or real exhausted-account notification was induced for testing.
